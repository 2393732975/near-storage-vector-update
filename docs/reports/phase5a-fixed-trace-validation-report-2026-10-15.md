# 阶段 5A 固定轨迹质量与性能门禁报告（2026-10-15）

## 结论

阶段 5A 固定轨迹验证通过。实验对同一份冻结的 GIST1M HNSW 基础图执行控制组
（M2、关闭只读执行器）和优化组（250 μs、5 个执行器线程），消除了独立建图
随机性。并行度 1 的 200 次更新中，目标 label、插入 global ID、节点 level、候选
集合哈希和 Recall 样本完全一致，`exact_mismatch_count=0`，两组 Recall@10 均为
0.418。这证明只读执行器没有改变串行 HNSW 更新语义。

并行度 4 的三轮固定 200-update 对照也全部通过质量和性能门禁：平均延迟降低
20.61%，P99 降低 15.97%，吞吐提高 25.55%。8/8 个 update 运行均零失败，
8/8 次 checker 均为 `pass`、0 error、0 warning。阶段 5A 因而可以进入四数据集
正式 A/B，但这不代表完整阶段 5 已完成：物理 CLS 调用只下降约 8.9%，跨 update
合批仍然很弱，修改型 edge patch 微批仍被阶段 4 的恢复协议门禁阻塞。

## 确定性语义门禁

串行控制组先构建并保存基础图，优化组从相同 cache 加载。比较器要求共同的 200
个 query 全部存在，并对每条记录逐字段比较更新轨迹。

| 指标 | M2 控制组 | Stage 5A | 结果 |
| --- | ---: | ---: | --- |
| 更新数 | 200 | 200 | 一致 |
| Recall hits / denominator | 836 / 2000 | 836 / 2000 | 一致 |
| Recall@10 | 0.4180 | 0.4180 | 差值 0.000 pp |
| 轨迹字段不一致数 | — | 0 | pass |

该门禁回答的是“优化是否改变算法语义”。并行更新的完成顺序仍受调度影响，因此
并行配置使用配对 Recall 和多次重复评估，而不要求完整轨迹逐条相同。

## 对此前质量失败的解释

并发度消融中的 Recall 波动来自控制组和优化组分别重新构建了随机 HNSW 基础图，
再叠加并行提交顺序差异。新版 importer 的 `build/load` cache 模式使每对实验导入
完全相同的节点 level 和邻接结构。冻结基础图后，串行轨迹 0 mismatch，并行三轮
Recall 差值全部位于允许的最多 0.5 pp 退化范围内，说明此前失败不能归因于
250 μs 等待窗口或只读执行器改变搜索算法。

## 阶段决策

1. 冻结 Stage 5A 候选参数：等待 250 μs、执行器线程 5、正式并行度 4；并行度
   8 继续排除。
2. 进入四数据集、三次重复、同基础图配对的 OSD-only 正式 A/B；每轮同时保留
   结构检查、语义检查和共同前缀 Recall 门禁。
3. 默认开关在四数据集 A/B 完成前仍保持关闭，不能仅凭 GIST1M 启用。
4. 完整阶段 5 的 60% 调用数下降目标尚未达到。下一性能重点是 per-target
   inflight/queue 控制和图感知布局；修改型写微批必须等待阶段 4。
