# 项目问题评估与后续验证报告（2026-11-12）

本项目已经建立严格的 compute/raw-RADOS 与 OSD/CLS 对照，并在正式实验中通过了
相应的一致性和质量检查。当前主要障碍是：细粒度远端调用仍然很多，异步优化的
尾延迟收益不稳定，跨对象故障恢复尚未实现，长期动态质量与空间稳态尚缺验证。

## 1. 细粒度 RPC 和对象扇出仍是核心性能障碍

### 事实与证据

[阶段 1 严格 A/B 报告](phase1-strict-raw-vs-osd-report-2026-09-30.md)显示，compute
距离阶段的 98.79%–99.84% 用于拉取候选向量；OSD 卸载后，真正算距只占距离阶段
的 0.07%–0.77%。近存储计算已经减少了候选向量返回客户端的需要，但大量小请求
仍然保留。

[阶段 5A 正式报告](phase5a-four-dataset-formal-ab-report-2026-10-27.md)中，物理
CLS 调用数只减少 1.74%–8.60%，每个物理 RPC 的逻辑子请求数只有 1.018–1.079。
Deep100M 一次更新触达约 363 个距离对象，跨 update 合并机会尤其有限。

[阶段 6 报告](phase6-deep100m-inflight-scan-report-2026-11-12.md)的 Deep100M
数据进一步表明，固定 inflight 上限几乎不改变调用形态：

| 配置 | CLS calls/update | 距离 RPC/update | subrequests/RPC | 距离阶段 | 邻接 patch |
| --- | ---: | ---: | ---: | ---: | ---: |
| uncapped | 731.84 | 569.38 | 约 1.018 | 324.918 ms/update | 83.481 ms/update |
| cap=1 | 731.65 | 569.21 | 约 1.018 | 313.022 ms/update | 85.388 ms/update |

### 为什么会出现这个问题

一次 HNSW 更新需要逐步搜索图。当前候选的距离结果会决定后面继续访问哪些节点，
因此不能把整次更新需要的对象一开始就全部列出并一次性读取。

同时，[当前 PlacementResolver](../../include/nsvu/placement.hpp)按 global ID
取模选择 owner，再按固定容量划分对象。这个规则易于计算，但没有让图中相近的
节点优先处于同一对象。搜索得到的一组邻居分散到很多对象后，每个对象往往只剩
一个候选。

CLS 的对象内操作边界又限制了一次请求能访问的数据。节点落在同一个 OSD 或 PG，
仍不等于它们位于同一个对象，不能据此把多个对象合并成一次对象内原子操作。

“异步”让几个独立对象的等待时间重叠；“合批”减少实际发出的请求数量。当前主要
收益来自前者。`subrequests/RPC=1.018` 表示平均每个 RPC 只承载约 1.018 个逻辑
子请求，不能表述为已经实现充分合批。

### 影响与证据边界

数百次小请求会持续消耗调度、编码、对象读取和往返时间，限制仅靠算距内核优化
获得的收益。阶段 5A 的 Deep100M payload 与 patch 耗时分别增加 12.58% 和
20.25%，也说明距离等待减少后，其他阶段仍可能抵消端到端收益；这些增加的具体
原因还需逐 update 关联验证。

按现有布局估算，Deep100M 整次更新的候选/唯一距离对象仅约 1.64。这个值是整次
更新内的平均对象复用潜力，不能当成同步 frontier 当前就能达到的批大小，也不能
通过把不同 query 装进一个 RPC 而宣称提高了单 query 的候选密度。

### 建议处理与验收

继续分别记录距离 RPC、全部 CLS 调用、候选/逻辑子请求、子请求/物理 RPC、query
bytes 和对象扇出。判断优化是否有效时，先明确减少的是调用数、数据量还是等待。

若阶段 6 复测仍不能稳定改善，应按阶段 7 评估有界图感知布局，重点减少距离对象
扇出，并同时约束对象大小、OMAP、负载与迁移成本。现有计划中的扇出降低至少 30%
等目标是待验收目标，不能作为预期必然收益。任何调用数改善仍需通过质量、平均
延迟和 P99 门禁；修改型 patch 聚合必须先通过阶段 4 恢复门禁。

## 2. 性能优化尚未形成跨数据集稳定成立的结果

### 已确认的三组结果

阶段 3、5A、6 对应不同机制，不能把它们合称为一次成功的“批处理优化”。

| 机制 | 已有结果 | 当前判断 |
| --- | --- | --- |
| 阶段 3 同步 frontier 聚合 | 自适应版本距离批次仅减少 1.19%–3.33%，平均延迟增加 3.17%–8.63% | 可行性失败，负面结论关闭 |
| 阶段 5A 异步读取与跨 update 微批 | 三个数据集性能通过；Deep100M 平均延迟下降 6.25%，P99 增加 23.58% | 整体性能门禁失败，默认关闭 |
| 阶段 6 固定 inflight 上限 | cap=1 三轮均值改善，但两轮平均延迟与 P99 回退 | 保留复测候选，默认上限仍为 0 |

依据：[阶段 3 可行性报告](phase3-frontier-feasibility-report-2026-10-10.md)、
[阶段 5A 正式报告](phase5a-four-dataset-formal-ab-report-2026-10-27.md)、
[阶段 6 正式报告](phase6-deep100m-inflight-scan-report-2026-11-12.md)。

### 原因解释与逐轮证据

阶段 3 为寻找同对象的合并机会，需要提前读取更多 frontier 邻接，甚至计算本来
不必访问的候选。它增加的预取和投机工作，抵消了节省的距离调用。已经修复的搜索
终止条件缺陷不应继续列为当前 bug；修复后的实验仍然没有通过性能门禁。

阶段 5A 的 Deep100M 出现“平均更快、尾部更慢”：P99 从 M2 的 944.340 ms 增至
1167.051 ms，第三轮 P99 回退 61.92%。P99 描述最慢部分更新的延迟边界，平均值
改善不能抵消它对服务稳定性的影响。排队、读写竞争和底层活动是待检验解释，目前
没有足够证据把回退归到其中一个原因。

阶段 6 的 `cap=1` 指每个目标对象最多有一个距离 RPC 正在执行，不是整个 OSD
只能处理一个请求。它的三轮结果为：

| 重复 | uncapped 平均延迟 / P99 | cap=1 平均延迟 / P99 | 平均延迟变化 | P99 变化 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 439.403 / 794.330 ms | 487.609 / 1075.330 ms | +10.97% | +35.38% |
| 2 | 560.147 / 4085.520 ms | 440.225 / 772.496 ms | -21.41% | -81.09% |
| 3 | 438.908 / 793.230 ms | 461.978 / 897.664 ms | +5.26% | +13.17% |

三轮 P99 的均值下降 51.60%，主要因为第二轮 uncapped 的 4085.520 ms 拉高了
对照均值。该值是第二轮的 P99，不是某一个已定位 update 的耗时。第二轮也不能
简单当成无效数据删除。

cap=1 共限制 28,407 个子请求，占约 0.699%，说明机制实际生效；cap=2 仅限制
6 个，cap=4 从未触发。后两者即使均值变好，也不能把变化归因于限流。

### 影响与证据边界

每配置只有三次重复，P99 的区间很宽，运行顺序、缓存和后台活动仍可能影响结果。
现有证据支持“cap=1 值得复测”，尚不支持“cap=1 稳定提速”或“它已经消除了
同目标拥塞”。自动门禁的 pass 范围见第 9 节。

### 建议处理与验收

先冻结统计定义、主要比较分母、重复次数和停止条件，再复用现有 cache 交替执行
uncapped/cap=1。保留所有有效轮次，报告逐轮配对差值、均值、区间与运行环境，
并明确是否要求逐轮不回退或允许何种尾延迟容差。

增加重复次数不保证得到正面结果。“稳定轮仍回退”或“证据仍不确定”都应允许成为
正式结论。若结果不支持调度收益，应停止推进 AIMD，转向对象扇出和调用形态；若
Deep100M 通过预先约定门禁，再进行四数据集回归。

## 3. 逐 update 的尾延迟关联仍不完整

### 已有观测与缺口

当前已经记录更新总延迟、整体阶段累计耗时，以及逐 owner/chunk target 的 queue、
RPC、CLS service、推导 roundtrip/queue 分位数、峰值 inflight 和限流计数。阶段 6
补齐了逐目标分布，不能再概括为“只有全局平均值”。

仍然缺少的是：将某一次慢更新与它提交的逻辑子请求、物理 RPC、目标对象、限流
事件和后续 patch 阶段连接起来。源码中的 `RunUpdateParallel` 保存更新总耗时；
`DistanceReadExecutor` 汇总目标级指标，但现有输出不足以重建慢更新的关键路径。
依据：[Coordinator](../../src/coordinator/update_coordinator.cc)以及
[阶段 6 报告的尾部观测](phase6-deep100m-inflight-scan-report-2026-11-12.md)。

### 为什么整体分位数不能解释慢更新

一次更新包含很多请求。少数特别慢的请求如果落在依赖链上，会拖慢整次更新；同样
数量的慢请求若属于其他更新，或与独立请求重叠，对本次更新的影响可能不同。
只看全部 RPC 的 P95/P99，无法知道这些请求属于哪一次更新、出现在哪个阶段。

三个时间口径也必须保持分离：

| 指标 | 当前含义 | 不能直接推出的结论 |
| --- | --- | --- |
| executor queue | 客户端请求从入队到派发的等待 | 不能当作 OSD 队列时间 |
| CLS service | OSD 侧 CLS 内部执行计时 | 不能覆盖整个客户端 RPC 生命周期 |
| roundtrip/queue | 客户端 RPC 耗时减去 CLS 内部耗时 | 不能当作纯网络时间或纯 OSD 排队 |

cap=1 相对当轮 uncapped 的 executor queue P95 只改善 0.71%，推导
roundtrip/queue P95 只改善 3.23%，但三轮 update P99 均值下降 51.60%。这种差异
需要事件关联才能解释，不能仅凭两个聚合数字认定因果。

### 建议处理与验收

建议为 update、逻辑子请求和物理 RPC 保留可关联 ID，并在慢更新记录中提供：
距离阶段起止、各目标排队与限流、RPC/CLS 时间、patch 阶段、失败与重试，以及能
与集群事件对齐的时间信息。跨 query 微批必须允许一个物理 RPC 关联多个 update，
共享服务时间不能重复计作每次更新独占成本。

观测应采用有界缓冲、抽样或慢事件保留，避免记录本身显著干扰调度。验收包括：
关联链路能重建、缺失或丢弃率可测、并行耗时不被简单累加为墙钟时间、开启观测的
开销被单独比较。能够关联事件只代表定位能力提高；最终因果解释仍需有针对性的
对照实验支持。

## 4. 跨对象更新缺少进程崩溃后的恢复协议

### 事实与证据

当前实现具备对象内幂等重试，但没有持久化的 Update Intent、完整 Saga 状态机和恢复器。更新依次创建新节点、写入邻接、修补其他节点邻接、完成全局元数据更新，再 CAS 切换 label，最后标记旧节点 stale。这些步骤涉及多个对象，无法作为一个原子操作提交。普通异常处理记录失败并结束该次尝试，没有针对整次更新执行自动补全或回滚。

依据为 [Coordinator 更新流程](../../src/coordinator/update_coordinator.cc) 中的 `RunUpdateParallel`、`InsertOneParallel`（基准提交 `b7395cc` 第 3353、3402、3898 行），以及[正确性基线](../correctness-observability-baseline.md)第 58–69 行。对象内幂等重放已验证，与跨对象崩溃恢复是不同能力；[实施计划阶段 4](../optimization-implementation-plan.md)第 366–389 行明确将后者列为待实现工作。

### 解释与具体例子

“同一笔写请求再执行一次不会重复生效”，不能推出“更新做到一半断电后能够继续”。例如新节点及邻接已经写入，但 label 尚未切换时进程退出，重启后的程序需要知道这笔更新的旧、新节点和已完成步骤。若 label 已切换而旧节点尚未标 stale，则需要补做状态切换。当前没有持久事务记录来支撑这些判断，checker 可以报告不一致，却不负责恢复。

当前成功路径可以概括为下图；这些步骤跨对象执行，各步骤之间都可能发生中断。

```mermaid
flowchart LR
    A[分配 ID 并写新向量] --> B[写新邻接]
    B --> C[修补其他节点邻接]
    C --> D[完成全局元数据更新]
    D --> E[CAS 切换 label]
    E --> F[标记旧节点 stale]
```

### 影响与证据边界

这限制了故障后自动恢复、多 Coordinator 完整事务语义，以及跨 update 修改型批处理。正式实验的零失败、checker 通过，证明已完成运行满足相应检查；不能替代逐阶段崩溃注入。本报告未执行此类故障注入，不认定正式结果已经出现孤立节点或计数漂移。

### 建议处理与验收

按阶段 4 设计持久化 intent，明确节点准备、激活、label 切换、旧节点失效和提交的状态转移及重放规则，再实现恢复器。验收应在每个持久化边界注入退出与响应丢失，重启后自动完成或按定义终止更新；重复恢复应收敛，checker、label 映射和计数均通过。恢复门禁通过后再评估修改型微批。上述为建议，尚未实施。

故障实验还应保存中断位置、恢复前后的持久状态和最终检查结果，区分“请求实际未执行”与“已执行但响应丢失”。只在正常运行后重放成功请求，无法覆盖这两类故障之间的恢复决策。

## 5. 多 Coordinator 并发超出当前完整验证范围

### 事实与证据

raw-RADOS 路径使用进程内静态 mutex 协调多个 worker 的读改写。`RawCasLabel` 先读取 label，在客户端检查预期值，再写回；ID 预留和邻接 patch 也依赖相应锁。它们适用于当前一个 Coordinator 进程中的多线程，不能把锁的保护范围延伸到另一进程。

证据见 [Coordinator](../../src/coordinator/update_coordinator.cc) 的 `raw_meta_mutex`、`raw_object_mutex`、`RawCasLabel`、`RawReserveInsert`（`b7395cc` 第 832、1976、2289 行）。CLS 路径具有对象内原子 CAS，但[实施计划](../optimization-implementation-plan.md)第 368 行仍将多 Coordinator 扩展列为阶段 4 的目标。

### 解释与具体例子

两个线程可以争用同一把进程内锁；两个独立程序各自持有一把锁，并不会互相等待。两个 raw Coordinator 若同时读到相同 label 或 ID 分配状态，各自在本进程内检查成功，仍可能先后覆盖对方的写入。CLS 的对象内 CAS 能约束单个对象，却不能替代跨对象更新的恢复和提交协议。

### 影响与证据边界

当前“并发度 4”主要指单进程内四个更新 worker，不能据此宣称支持四个独立 Coordinator。这个限制不否定现有单进程 raw/CLS A/B 的结果；上述跨进程竞争是根据锁作用域推导的风险，本报告没有运行多进程竞争实验。

### 建议处理与验收

先明确产品与实验需要的并发范围。若需要多进程，应为 raw 路径补充保持零 CLS 的服务端条件写或等效协调机制，并结合阶段 4 统一 ID、版本和恢复语义。验收覆盖多个独立进程更新同一 label、不同 label 和重叠邻接，检查 ID 唯一、无并发覆盖造成的 patch 丢失、正常邻接度数裁剪符合既定规则、label 指向正确及冲突可检测；同时加入进程退出恢复。新增保证应与单进程性能结果分别报告。

## 6. 当前 Recall 门禁未覆盖更新后动态语料的完整质量

### 事实与证据

现有 Recall 来自插入搜索的 level-0 候选，并与原始 base 的 ground truth 比较。[实验手册](../experiment-runbook.md)第 336–339 行明确说明，这是更新提交前的静态回归指标，动态语料精确 Recall 需要重新计算 ground truth。实现见 [Coordinator](../../src/coordinator/update_coordinator.cc) 的 `InsertOneParallel` 和 `RecordRecall`（`b7395cc` 第 3868、3915 行）。

[固定轨迹报告](phase5a-fixed-trace-validation-report-2026-10-15.md)已经提供串行轨迹一致与并行配对质量证据，但本次审查未找到针对长期更新后有效向量集合的独立查询、精确 GT 重算及正式稳态报告。

### 解释与具体例子

原始 GT 回答的是“初始数据库中哪些向量最近”。如果其中一个向量已被替换，当前正确答案可能变化：仍按原 GT 命中旧节点，不代表检索到了有效结果；检索到新插入的正确近邻，也可能不计入原 GT 的命中。共同 query 前缀改善了 A/B 的可比性，却不会把旧 GT 自动变成当前 GT。

### 影响与证据边界

现有指标可用于发现优化带来的搜索行为变化，但不足以证明持续更新后的用户查询质量。这里的问题是验证范围，不是已经观察到动态 Recall 下降，也不意味着现有配对检查无效。

### 建议处理与验收

保留现有回归门禁，另增加动态评估：在可精确计算 GT 的数据规模上，按固定更新轨迹形成多个检查点；冻结每个检查点的有效 label—向量集合，用独立查询集计算当前精确 GT，再运行检索。分别报告 Recall、无效或重复 label 返回，以及延迟随累计更新量的变化。质量阈值应实验前冻结；如沿用既有 0.5 个百分点最大退化线，须明确它比较的是同一动态检查点的配对结果。

## 7. stale 节点长期累积缺少回收机制与稳态验证

### 事实与证据

当前替换为新节点分配新 ID，写入新向量；`cls_mark_node_stale` 仅修改旧 `VectorRef.flags`，不删除旧 payload 或邻接。证据见 [CLS stale 实现](../../src/cls/hnsw_cls.cc)（`b7395cc` 第 832–853 行）与 [Coordinator 新节点创建](../../src/coordinator/update_coordinator.cc)第 3823–3831 行。本次在源码、工具和正式报告中未找到面向持续更新索引的 stale 回收、按当前有效语料压缩重建流程或长期空间稳态验证。现有 importer 可以构建基础 HNSW 图，这不等于已经具备维护动态索引的回收重建流程。

### 解释与具体例子

同一业务 label 连续替换多次，业务上只保留最新向量，存储中却会留下多个历史节点。标 stale 可以表达“这个版本已经失效”，但不会自动释放其向量和图数据。旧节点还可能参与图路由，直接删除需要处理邻接与可达性，不能把回收简化成删除 payload。

### 影响与证据边界

持续运行会累积历史数据；它对对象大小、OMAP、搜索路径及尾延迟的实际影响尚未量化。现有每轮重新建池、重新导入后的短时实验，适合比较更新机制，尚不能代表长期空间和性能稳态。本报告没有证据认定某一比例的 stale 已造成质量或延迟退化。

### 建议处理与验收

先增加累计替换实验，记录 live/stale 数、payload 与 OMAP 占用、对象数、距离调用、动态 Recall 和 P99。再据增长曲线选择离线重建或有界回收策略，并明确 stale 节点在路由和最终检索结果中的处理规则。验收需证明容量增长符合预先声明的保留上限，回收后图与映射检查通过，动态质量和尾延迟不越过门槛；若涉及在线迁移，还须验证中断恢复。具体上限由实验确定，不在本报告中预设收益。

## 9. 门禁、统计分母、文档和复测工具存在口径缺口

### 9.1 “三轮不回退”与“均值不回退”没有清楚区分

[实施计划](../optimization-implementation-plan.md)第 556–557 行写
“Deep100M 三轮 P99 不回退”；[阶段 6 runner](../../scripts/run-stage6-inflight-scan.sh)
第 193–227 行实际执行的是：

```text
control_p99 = mean(各轮 uncapped 的 P99)
candidate_p99 = mean(各轮候选配置的 P99)
latency_ceiling = 511.790 ms × 0.95 = 486.2005 ms

performance_pass = candidate_p99 <= control_p99
                   且候选的三轮平均延迟 <= latency_ceiling
```

再结合零失败、零 retry 和配对质量门禁，脚本决定 pass/fail。它不要求每一轮 P99
都不回退，也不把“限流必须实际触发”作为性能 pass 的条件。因此 cap=1 两轮回退、
cap=4 从未触发限流，仍然都可能显示 pass。

均值门禁本身可以使用，问题是必须把含义写明。这个 pass 只表示当前公式通过，
不表示机制产生了因果收益、不表示每轮稳定，更不表示整个阶段 6 已经完成。应在
下一轮前明确质量、机制生效、均值性能、逐轮稳健性和完整阶段退出各自的判据。

### 9.2 完整退出门槛混用了历史与当轮分母

计划要求 queue estimate P95 和 update P99 相对阶段 5 至少下降 20%。现有
阶段 6 报告中的 update P99 改善 21.58% 对比历史阶段 5A；queue 的 0.71% 和
roundtrip/queue 的 3.23% 则对比本轮 uncapped。

本次核对的历史阶段 5A Deep100M 六份 update JSON 没有相应 queue P95/P99，
所以无法从这些工件直接重建历史分位数。不能用平均 queue 代替 P95，也不能将
缺失字段后补为“历史实测值”。

建议下一轮明确以同提交、同 cache 的 uncapped 作为重跑的阶段 5A 行为控制，
让 update P99 与 queue 指标使用同一对照；历史数据仅作趋势参考。同时需事先
确定 queue 门槛指客户端 executor queue，还是推导 roundtrip/queue。本报告
不重写历史验收结果，也不据此宣称阶段 6 通过。

## 10. 建议处理顺序与交付标准

近期性能主线与恢复主线可以分别推进，但修改型批处理仍必须等待恢复门禁。

| 顺序 | 工作 | 预期交付物 | 判定原则 |
| --- | --- | --- | --- |

| 2 | 补充逐 update 关联与 cache 加载入口 | 有界观测、关联样本、开销对照、cache manifest | 数据可关联、开销可测、基础图来源可复核 |

| 4 | 根据复测决定性能方向 | AIMD 是否有必要的证据；或阶段 7 可行性方案 | 不因阶段编号顺序强行实现没有证据支持的机制 |

| 长期验证 | 动态查询质量与累计替换实验 | 当前有效语料 GT、空间/质量/延迟曲线 | 先建立长期边界，再选择回收与布局方案 |
