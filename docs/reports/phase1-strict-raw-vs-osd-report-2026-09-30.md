# 阶段 1 Strict Raw-RADOS/OSD A/B 报告（2026-09-30）

## 结论

严格 A/B 已完成：四个数据集、两条路径、三次独立重导入，共 24/24 轮、
55,023 次成功更新。所有轮次均为 `failed_updates=0`，24 次离线检查全部
`status=pass`、`errors=0`、`warnings=0`，抽样图边语义胜率为
0.991346–1.000000。

本轮首次实现了定义严格的 compute baseline：完整更新协议只调用原生 librados，
不再借用 CLS 完成 label、邻接、patch 或全局元数据操作。所有 compute 轮次均为
`storage_access_mode=raw_rados` 且 CLS 调用严格为 0；所有 OSD 轮次均为
`storage_access_mode=cls` 且确实产生 CLS 调用。

OSD 卸载在四个数据集上均获得稳定的方向性收益：三轮平均延迟降低
12.67%–22.32%，吞吐提高 14.33%–29.39%。这说明与全链路原生 RADOS 相比，
OSD 内对象级操作能够减少客户端往返；但 OSD 路径仍有约 501–747 次 CLS
调用/update，远端距离阶段仍占约 70% 的更新延迟，尚未解决细粒度 RPC 瓶颈。

## 调用粒度与方案修正

| 数据集 | compute Raw calls/update | OSD CLS calls/update | 距离批次/update (compute/OSD) | 候选/批次 | 数据 KiB/update (compute/OSD) |
| --- | ---: | ---: | ---: | ---: | ---: |
| Deep100M | 1290.78 | 747.22 | 588.25 / 589.50 | 1.009 | 294.83 / 285.24 |
| GIST1M | 954.31 | 500.60 | 426.75 / 418.40 | 1.11 | 1834.01 / 1618.55 |
| SIFT100M | 1279.10 | 718.45 | 583.42 / 584.77 | 1.016 | 145.92 / 136.37 |
| Text2Image10M | 1134.87 | 610.07 | 510.28 / 505.16 | 1.030 | 474.63 / 450.79 |

当前优化方案的方向无需推翻，但优先级应进一步收敛：

1. 首先把同一搜索 frontier 中属于同一对象的候选聚合，目标是
   `candidates/batch >= 8`、`distance batches/update < 80`；不能继续以单候选
   CLS 调用作为主要执行形态。
2. 聚合后再实施跨更新微批与拥塞感知调度，否则排队优化会被数百次同步依赖抵消。
3. 邻接 patch 维持对象内原子执行，同时按 owner/object 合并；距离批次下降后，它将
   成为约 60–92 ms/update 的下一瓶颈。
4. global meta 目前只有约 1.7–2.8 ms/update，不是阶段 1 的首要优化对象；分片元数据
   协议仍有扩展价值，但应排在距离聚合和邻接聚合之后。

旧的混合路径报告中，compute 仍调用 CLS，OSD 相对延迟变化只有 -2.16% 至
+2.42%。本轮严格 raw baseline 显示 -12.67% 至 -22.32%。两组数字的差异来自
baseline 定义修正，不能解释为同一实现经过优化后的纵向加速。

## 限制与收尾

- Recall 是更新提交前 level-0 搜索相对原始 base ground truth 的静态指标，不是
  更新后动态语料库的精确 Recall。
- 每轮导入会预热客户端与 OSD 缓存，结果不能解释为冷缓存性能。
- `roundtrip/queue` 包含网络、librados、OSD 排队与线程调度，不能单独归因为网络。
- compute 原生 read-modify-write 锁只覆盖单 Coordinator 进程；本实验不验证多
  Coordinator 并发事务语义。
- 正式结果由 `summary.md` 和 `summary.json` 自动汇总；报告提交后，实验池使用带
  FSID 保护的白名单清理脚本删除，并单独记录最终集群状态。
